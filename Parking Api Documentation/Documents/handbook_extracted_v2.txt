2	Scope
This handbook is the single entry point for implementing a client application that talks to the Remote Parking Server (RPS) API. It consolidates, in reading order:
The HMAC-SHA256 authentication scheme used by every terminal endpoint.
The wire contract for the six parking endpoints that drive a vehicle's entrance, exit, and payment lifecycle.
Operational guidance for onboarding, debugging a 401 Unauthorized, and rotating shared secrets.
Companion artifacts shipped alongside this document:
src/RPS.HmacSample/ — a runnable C# reference implementation of the request-signing logic, intended to be ported into the client app.
Documents/Parking_App_API.postman_collection.json — Postman 2.1 collection with all six endpoints, auto-signed by a collection-level pre-request script. Useful for smoke-testing against the dev sandbox before any client-app code exists.

3	How to read this document
The chapters are ordered so that a developer can read top-to-bottom and have working code by the end:
Chapter 1 (Integration Guide) gives the 60-second mental model and an onboarding checklist.
Chapter 2 (HMAC Terminal Auth) is the normative authentication spec — every other chapter assumes this is in place.
Chapters 3 – 8 are the per-endpoint contracts. Each one is self-contained and follows the same template: purpose, request schema, response schema, error handling, worked examples.
Code blocks are reproduced verbatim from the source markdown. JSON payloads in the request/response examples are the same fixtures used by the C# sample app and the Postman collection, so values are directly comparable across all three artifacts.

4.1	Summary
RPS exposes six HTTPS endpoints that the parking terminal calls during normal operation. Every one of them is protected by an HMAC-SHA256 scheme that we ship under the literal token hmacauth:
Authorization: hmacauth <clientId>:<signature>:<nonce>:<timestamp>
clientId identifies the terminal (assigned by us per device).
signature is HMAC-SHA256(secret, sigBase) where secret is the decoded Base64 of the per-client shared secret and sigBase is the canonical string defined in HMAC_TerminalAuth.md §1.
nonce is 16 random bytes hex-encoded — fresh per request.
timestamp is Unix epoch seconds (not milliseconds — common bug).
The server rejects unknown clients, stale timestamps (±5 min by default), replayed nonces (same clientId+nonce within 10 min), and signature mismatches with a 401 whose WWW-Authenticate header explains exactly which check failed (catalogue in §7).

4.4.3	What to study in ParkingHmacSigner.cs
keyBytes    = Convert.FromBase64String(secretBase64)
bodyHash    = base64(SHA256(body))           // empty span for GET
timestamp   = unix-epoch-SECONDS, decimal string
nonce       = 16 random bytes, hex (lower-case)
encodedPath = lower-case URL-encoded path+query  ("/api/parkinginit?..." → "%2fapi%2fparkinginit%3f...")
sigBase     = clientId + METHOD + encodedPath + timestamp + nonce + bodyHash
signature   = base64(HMAC-SHA256(keyBytes, UTF-8 bytes of sigBase))
header      = "hmacauth " + clientId + ":" + signature + ":" + nonce + ":" + timestamp
That's the entire scheme. Take into consideration the following:
timestamp is seconds, not milliseconds. Date.now() / 1000 in JS; System.currentTimeMillis() / 1000 in Java/Kotlin. The server rejects anything > 5 min off either way.
The path is URL-encoded and lower-cased before being signed. Sign exactly what's in Request.Path + QueryString, not the full URL with scheme/host. (Scheme/host are deliberately not signed — see HMAC_TerminalAuth.md §1 for why.)
bodyHash is over the exact bytes you send. If your HTTP client re-serialises the JSON (re-orders keys, re-spaces, changes number format) between sign-time and send-time, the server's recomputed hash won't match yours. Serialise once, sign that exact byte buffer, send that exact byte buffer.
secret is decoded before being used as the HMAC key. The stored format is Base64; the key passed to HMAC-SHA256 is the raw 32 bytes that Base64 decodes to. Don't HMAC with the Base64 string.
Fresh nonce every request. Even a 50-ms retry must mint a new one — the server caches (clientId, nonce) for 10 minutes and replies 401 replay on the second sighting.
The sample also runs a ValidateCanonicalSecret(...) check at startup to catch a subtle Base64 footgun where two different strings decode to the same bytes — read the XML doc comment on that method, it's worth five minutes.

4.7	Debugging a 401
The server's WWW-Authenticate response header carries an error="…" parameter that pinpoints which check failed. Match the value to this table and you've usually solved it in five minutes.
[TABLE START]
error value || What it means || First thing to check
missing_credentials || No Authorization header at all || Your sign-and-send code didn't run; or the wrong endpoint (e.g. an admin endpoint expecting JWT)
invalid_scheme || Header doesn't start with hmacauth || Token shape; check for missing space after hmacauth
invalid_header || Less than 4 colon-separated parts || Truncated header; nonce/timestamp dropped
invalid_timestamp || Non-numeric timestamp || Sent milliseconds instead of seconds, or sent ISO-8601 string
clock_skew || ` || now − ts
unknown_client || clientId isn't provisioned on this environment || Typo; or you're using a UAT clientId against the prod server
invalid_signature || The server's recomputed signature differs from yours || The big one — see "Signature mismatch checklist" below
Replay || Same (clientId, nonce) seen within the cache window || Your nonce generator is reusing values; or a retry isn't minting a fresh one
server_misconfiguration || Server-side secret is not valid canonical Base64 || Tell us — this means the server's appsettings/Vault entry is wrong, not your client
[TABLE END]
4.7.1	Signature mismatch checklist
When you get invalid_signature, walk this list top-to-bottom:
Did the body change between sign and send? Serialise to a byte array once, hash that array, send that array. Don't let an HTTP-client middleware (logging interceptor, content-encoding, pretty-printer) modify the body after you've signed it.
Is timestamp in seconds? Print it. A 10-digit number is seconds; a 13-digit one is milliseconds.
Is the path lower-cased after URL-encoding? "/api/parkingInit" → URL-encode → "%2Fapi%2FparkingInit" → lower-case → "%2fapi%2fparkinginit". Both transformations, in that order.
Is the secret being decoded before use? HMAC(Base64.decode(secretBase64), sigBase), not HMAC(secretBase64, sigBase). The Base64 string and the raw 32 bytes look identical when wrong, but produce different MACs.
Encoding everywhere is UTF-8. No platform default-charset surprises.
nonce is hex, lower-case. 0xA3 → "a3", not "A3" or "ÿ".
If you've checked all six and it still mismatches, turn on the sample's debug logging (or Postman's), paste the sigBase lines from both sides, and a byte-diff will pin it down. We can also enable Debug-level logging on the server to print the same field on our end on demand.

5	HMAC authentication for parking terminal endpoints
This document describes the HMAC-SHA256 authentication scheme that protects the parking-terminal-facing API endpoints:
[TABLE START]
Endpoint || Method || Controller
/api/parkingInit || GET / POST || ParkingInitController
/api/entranceCall || POST || EntranceCallController
/api/exitCall || POST || ExitCallController
/api/exitPayment || POST || ExitPaymentController

5.1	Wire format
A single Authorization header carries everything the server needs:
Authorization: hmacauth <clientId>:<signature>:<nonce>:<timestamp>
[TABLE START]
Component || Encoding || Notes
hmacauth || literal || Lower-case scheme prefix. Matches the JCC IPPI scheme we already implement on the outbound side.
clientId || UTF-8 string || Identifies the terminal/client. Must match a key in Hmac:Clients (or fall through to Hmac:DefaultSecretKey).
signature || Base64 || HMAC-SHA256(secret, sigBase) (see below).
Nonce || hex || 16+ random bytes hex-encoded. Each (clientId, nonce) pair is rejected on a second sighting within the cache window.
timestamp || decimal || Unix epoch seconds. Rejected if |now - ts| > Hmac:ClockSkewSeconds.
[TABLE END]
The signature base string is exactly:
sigBase = clientId
        + METHOD                                      # "POST", "GET", upper-case
        + lowercase(percent_encode(path + query))     # "/api/parkinginit?outlet=..."
        + timestamp                                   # epoch seconds, decimal
        + nonce                                       # hex, lower-case
        + base64(SHA256(rawBody))                     # SHA256("") for empty bodies
The bytes signed are the UTF-8 encoding of sigBase. The HMAC key is the decoded Base64 value of the configured client secret (so the secret can carry binary entropy without JSON-escaping issues).
5.1.1	Worked example
For a POST /api/parkingInit to https://parking-api.example.com:443/api/parkingInit with body {"application":"Parking","outlet":"0000259010","terminal":"000025901025"}, clientId MarinaParking-T01 and secret Y2hhbmdlbWUtZGV2LXNoYXJlZC1obWFjLWtleS0wMDAwMDAwMDAwMDAwMDA=:
clientId     = "MarinaParking-T01"
method       = "POST"
pathQuery    = "/api/parkingInit"
encodedPath  = "%2fapi%2fparkinginit"
timestamp    = "1747140000"
nonce        = "9f8a1c2b4d6e7f0a1b3c4d5e6f708192"
bodyHash     = "yXkUO7gmJ0VqxvHnQH+...=" (SHA256 of the JSON above, Base64)
sigBase      = "MarinaParking-T01POST%2fapi%2fparkinginit17471400009f8a1c2b...yXkUO7gmJ0VqxvHnQH+...="
signature    = base64(HMAC-SHA256(decodeBase64(secret), UTF8(sigBase)))
authHeader   = "hmacauth MarinaParking-T01:<signature>:9f8a1c2b...:1747140000"
If the server's recomputed signature differs by a single byte, you get a 401 with WWW-Authenticate: hmacauth realm="rps", error="invalid_signature". Common culprits: trailing / mismatch, body re-pretty-printing, query- string variable substitution, Date.now() / 1000 vs Date.now() (epoch seconds, not milliseconds).

The collection (RemoteParkingServer.postman_collection.json) already ships with:

Override hmac_client_id and hmac_secret in a Postman environment (not the collection variables) so the production secret never lands in a collection export.

5.2.3	Debugging a 401
When the script's debug flag is true, it logs clientId, method, pathQuery, encoded, timestamp, nonce, bodyHash, sigBase, and signature to the Postman Console (Ctrl+Alt+C). The server logs the same fields under RPS.Api.Authentication.HmacAuthenticationHandler at Warning level on every failure (HMAC auth failed: ... for ClientId=...), so a side-by-side diff of the two sigBase lines pins down byte-level mismatches in seconds.
The 401 response itself includes a WWW-Authenticate header whose error="..." parameter explains the failure:
[TABLE START]
error value || Meaning || First thing to check
missing_credentials || No Authorization header || The pre-request script didn't run; check the request is in the Parking App API folder.
invalid_scheme || Header doesn't start with hmacauth || Token shape; confirm script output.
invalid_header || Less than 4 colon-separated parts || Truncated header.
invalid_timestamp || Non-numeric ts field || Postman-side bug.
clock_skew || |now - ts| > ClockSkewSeconds || NTP-sync the client/server.
unknown_client || clientId not in Hmac:Clients and no DefaultSecretKey || Provision the terminal / fix typo.
invalid_signature || Recomputed signature differs || Body re-pretty-printing, path case, query substitution; see "Worked example" above.
replay || Same (clientId, nonce) seen recently || The script must use a fresh nonce per request — CryptoJS.lib.WordArray.random(16) already does this; suspect a manual paste.
server_misconfiguration || Configured secret isn't valid Base64 || Check appsettings*.json.
[TABLE END]
